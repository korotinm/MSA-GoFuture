Контекст задания: «GoFuture» хочет быстро запускать решения для партнёров (локальные такси-компании, банки, e-commerce) в новых регионах с полной изоляцией данных и кастомизацией функциональности. ## ADR 5.1. Модель мультитенантности и изоляции данных

### Контекст

Платформа должна принимать десятки и сотни партнёров. Часть из них (банки, регулируемые компании, крупные операторы) требует физической изоляции данных и собственных ключей, остальным достаточно логической изоляции. Выделять каждому отдельный стек дорого и не позволит запускаться за дни, но общий стек без изоляции недопустим.

### Требования

- Утечка данных одного тенанта другому невозможна даже при ошибке в коде сервиса.
- Один «шумный» тенант не ухудшает работу остальных.
- Тенант выбирает уровень изоляции, подключение нового занимает дни, а не месяцы.
- Кастомизация без форков кода.
- Изоляция действует на всех хранилищах (БД, события, кэш, аналитика, файлы).

### Решение

**Гибридная модель Pool + Silo.** Тариф изоляции хранится в Tenant Registry и определяет маршрутизацию ресурсов. Диаграмма: [C2_Data_Isolation.puml](C2_Data_Isolation.puml).

| Хранилище | Pool (по умолчанию) | Silo (по запросу, обязательно для регулируемых) |
|:--|:--|:--|
| PostgreSQL | Общий кластер, `tenant_id` во всех таблицах, **Row-Level Security** (политика по `app.tenant_id`), роль приложения без BYPASSRLS, партиционирование крупных таблиц по хэшу тенанта | Выделенный кластер (Patroni), отдельные креды из Vault, отдельный ключ шифрования |
| Kafka | Общие топики, `tenant_id` в конверте события, квоты по клиенту (producer_byte_rate), ACL по сервисам | Выделенные топики `t.<tenant>.*`, ACL только на сервис-аккаунты тенанта, свои квоты (при необходимости отдельный кластер) |
| Redis | Префикс ключей `t:{tenant}:`, ACL по пространству ключей | Выделенный инстанс |
| ClickHouse | Row policy по `tenant_id`, квоты запросов, BI-роли только для чтения | Отдельная БД и пользователи |
| Объектное хранилище | Префикс `tenant/{id}/` и политика бакета, шифрование ключом данных тенанта | Отдельный бакет, собственный ключ (CMK, возможно BYOK) |
| Ключи шифрования | Ключ региона плюс ключ данных тенанта (envelope encryption) | Выделенный CMK тенанта |
| Вычисления | Общие поды, квоты на запросы и параллелизм | Выделенный namespace или пул нод при необходимости SLA |
| Наблюдаемость | Метка `tenant_id` в агрегатах и логах, доступ тенанта через принудительный фильтр | Выделенный tenant в Loki и организация в Grafana |

**Критерии выбора silo:** требование регулятора или договора о физической изоляции, обязательность собственных ключей (BYOK), объём более порога (ориентир: более 5% общей нагрузки региона или более 100 тыс. поездок в сутки), особый SLA.

**Защита в глубину (три слоя).**

1. **Gateway:** тенант определяется из подписанного токена или API-ключа. Тенант, переданный клиентом в запросе или заголовке, игнорируется. Шлюз подписывает внутренний `x-tenant-id`.
2. **Policy (OPA):** `tenant_id` запроса должен совпасть с `tenant_id` ресурса, роль и регион разрешают действие. Решения пишутся в аудит.
3. **База данных (RLS):** даже при ошибке в коде сервиса запрос возвращает только строки текущего тенанта.

Пример политики RLS и контекста:

```sql
ALTER TABLE bookings ENABLE ROW LEVEL SECURITY;
ALTER TABLE bookings FORCE ROW LEVEL SECURITY;      -- действует и для владельца таблицы
CREATE POLICY tenant_isolation ON bookings
  USING      (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- в начале каждой транзакции (совместимо с PgBouncer в transaction-режиме):
BEGIN; SET LOCAL app.tenant_id = '8f1c...';  /* запросы */  COMMIT;
```

Пример политики OPA (Rego):

```rego
package gofuture.authz

default allow := false

allow if {
    input.token.tenant_id == input.resource.tenant_id   # тот же тенант
    input.token.region    == input.resource.region      # тот же регион
    role_actions[input.token.role][_] == input.action   # роль допускает действие
    mfa_ok                                              # MFA для чувствительных действий
}

mfa_ok if not input.resource.sensitive
mfa_ok if input.token.amr[_] == "mfa"
```

**«Шумные соседи».** Rate limit и квоты по тенанту на шлюзе (ответ 429 с `Retry-After`), лимиты соединений и `statement_timeout` на пул тенанта в БД, квоты Kafka, квоты запросов ClickHouse, классы приоритета подов. Превышение 80% квоты создаёт уведомление, 100% приводит к ограничению.

**Проверка изоляции как тест.** Набор автоматических тестов «cross-tenant»: токен тенанта A обращается к идентификаторам тенанта B во всех API, ожидание 403 или 404. Запускается в CI каждого сервиса, при онбординге (шаг O9) и по расписанию на проде (синтетика на тестовых тенантах).

**Кастомизация без форков.** Всё настраиваемое хранится как конфигурация тенанта в Control Plane:

| Что кастомизируется | Как |
|:--|:--|
| Тарифы и динамическое ценообразование | Правила и коэффициенты тенанта в Pricing (потолок множителя, зоны, расписания) |
| Платёжные и картографические провайдеры | Выбор провайдера по тенанту через абстракцию провайдера |
| Функции | Feature flags по тенанту и региону |
| Бренд | White-label: логотип, цвета, тексты, шаблоны уведомлений |
| Интеграции | Вебхуки и подписка на события тенанта (подписанные), API с квотами |
| Правила Fraud и подбора водителя | Параметры правил, а не код |

### Альтернативы

| Вариант | Почему не выбран |
|:--|:--|
| Silo для всех (БД и стек на тенанта) | Дорого, миграции схем множатся (N кластеров), онбординг дольше. Остаётся для тех, кому нужно |
| Схема на тенанта в одной БД (schema-per-tenant) | Миграции в сотнях схем, раздувание каталога PostgreSQL, сложное обслуживание. RLS проще при тысячах тенантов |
| Pool для всех без silo | Не подходит банкам и регулируемым партнёрам |
| Отдельный экземпляр платформы на партнёра | Нарушает цель «неделя вместо квартала» и разрастание версий |

### Компромиссы и риски

| Риск | Эффект | Смягчение |
|:--|:--|:--|
| Забытый `tenant_id` в новой таблице или запросе | Утечка данных между тенантами | RLS с FORCE, линтер миграций (таблица без `tenant_id` и RLS не проходит CI), cross-tenant тесты |
| RLS добавляет нагрузку на запросы (план запроса, индексы) | Рост латентности | Индексы с `tenant_id` в префиксе, нагрузочные тесты, партиционирование |
| Администратор БД обходит RLS | Утечка | Нет прямого доступа людей к продовым БД, доступ только JIT с аудитом |
| Миграция из pool в silo при росте тенанта | Простой и риск ошибки | Процедура миграции по аналогии с Task1: CDC, сверка, переключение по флагу |
| Дрейф конфигурации silo между тенантами | Различия в поведении | Провижининг как код (Crossplane и Terraform), контроль дрейфа |
| Рост числа топиков Kafka при silo | Нагрузка на контроллер | Лимиты на число silo-тенантов в кластере, переход на отдельный кластер для крупных |

## ADR 5.2. IAM: ролевая модель, SSO и политики доступа

### Контекст

На платформе несколько типов пользователей: конечные клиенты (пассажиры, водители), сотрудники партнёров, сотрудники GoFuture, а также машинные идентичности (сервисы, API партнёров). У партнёров уже есть корпоративные IdP, они ждут единого входа и автоматического управления учётными записями.

### Требования

- Единая аутентификация и SSO с корпоративными IdP партнёров (SAML и OIDC).
- Ролевой доступ (RBAC) с атрибутами (ABAC): тенант, регион, класс данных, уровень проверки.
- Автоматическое создание и блокировка пользователей (SCIM).
- Привилегированный доступ сотрудников GoFuture ограничен, временный и аудируемый.
- Резидентность: учётные записи пользователей хранятся в регионе.

### Решение

Компоненты показаны на [C2_Multitenant_IAM.puml](C2_Multitenant_IAM.puml) (синий цвет).

| Аспект | Решение |
|:--|:--|
| IAM-платформа | **Keycloak** (HA, 3 зоны) в каждом регионе. Realm на регион, **Organization = тенант**. Конечные пользователи, сотрудники партнёров и GoFuture в одном realm региона, различаются организациями и ролями |
| SSO для партнёров | Identity brokering: Keycloak выступает посредником к IdP партнёра (SAML 2.0 или OIDC). Определение тенанта по домену e-mail (home realm discovery). SP- и IdP-initiated вход |
| Жизненный цикл | **SCIM 2.0** (в Keycloak через расширение, например scim-for-keycloak, либо через промежуточный сервис провижининга): создание, изменение, блокировка пользователей из IdP партнёра. JIT-создание при первом входе как запасной вариант. Роли берутся из групп IdP через маппинг |
| Конечные пользователи | Телефон и OTP, социальный вход. Данные в realm региона (резидентность) |
| Машинные идентичности | Партнёрские API: OAuth2 client credentials, ключи ротируются, область (scope) и квоты на тенанта. Сервисы внутри платформы: SPIFFE-идентичность в mesh (mTLS), токены сервисов короткоживущие |
| Токены | JWT, срок жизни 5-15 мин, refresh с ротацией. Утверждения (claims): `tenant_id`, `roles`, `region`, `tier`, `amr` (метод проверки, MFA), `scope` |
| Авторизация | Шлюз проверяет подпись и срок (JWKS в кэше), OPA принимает решение по политике (RBAC плюс ABAC). Политики в Git, проверяются тестами |
| MFA | Обязательно для администраторов тенантов, финансовых ролей, всех сотрудников GoFuture. Step-up (повторное подтверждение) для чувствительных операций: смена банковских реквизитов, выплаты |
| Привилегированный доступ | Сотрудники GoFuture по умолчанию без доступа к бизнес-данным тенантов. Доступ по запросу (JIT): тикет, подтверждение владельца тенанта (если требует договор), срок не более 4 часов, запись сессии, аудит. Аварийный доступ (break-glass) с немедленным алертом |
| Разделение обязанностей | Выплаты утверждаются двумя людьми (4-eyes). Поддержка не может менять банковские реквизиты, финансы не видят PII пассажиров |
| Аудит | Все события входа, смены ролей, JIT-доступа и раскрытия PII в SIEM, журнал в неизменяемом хранилище. Владелец тенанта видит аудит своих администраторов |

### Альтернативы

| Вариант | Почему не выбран |
|:--|:--|
| Realm на тенанта в Keycloak | Плохо масштабируется при сотнях и тысячах тенантов (память и время старта). Organizations решает задачу в одном realm |
| SaaS CIAM (Auth0, Okta CIAM) | Дорого на масштабе 100 тыс.+ пользователей и сотнях тенантов, вопросы резидентности и зависимости от вендора |
| Собственная реализация аутентификации | Высокий риск безопасности и стоимости сопровождения |
| Только RBAC без ABAC | Не выразит правила «свой тенант», «свой регион», «с MFA» без взрыва числа ролей |
| Ролевая модель в каждом сервисе | Расхождение правил и сложный аудит. Централизованный PDP (OPA) |

### Компромиссы и риски

- IAM и OPA становятся критичными компонентами (Tier-0): при отказе никто не войдёт. Смягчение: HA на 3 зоны, кэш JWKS и решений OPA в шлюзе на короткий срок (при недоступности Keycloak действующие токены продолжают работать до истечения), отдельные учения по отказу IAM.
- Сложность настройки SSO у каждого партнёра: шаблоны, самообслуживание в Partner Portal, проверка метаданных IdP на этапе онбординга.
- Утечка токена: короткий срок жизни, привязка к устройству для мобильных клиентов, отзыв сессий по событию безопасности.
- Рассинхронизация ролей между IdP партнёра и платформой: SCIM плюс ежедневная сверка.
- Нужен процесс эксплуатации JIT-доступа (кто одобряет, SLA на одобрение), иначе поддержка будет искать обходные пути.

## ADR 5.3. Автоматизированный процесс онбординга партнёров

### Контекст

Целевая метрика бизнеса: запуск в новой стране за 2-4 недели. Большую часть этого срока занимают согласования и юридические процедуры, поэтому техническая часть должна занимать часы, а не недели, и не требовать ручной работы инженеров.

### Требования

- Самообслуживание партнёра с прозрачным статусом.
- Автоматический провижининг IAM, изоляции данных, конфигурации и мониторинга.
- Проверка юрлица (KYB) и ручное подтверждение для рискованных случаев.
- Идемпотентность и откат при сбое.
- Измеримые SLA по шагам.

### Решение

Диаграммы: [C2_Multitenant_IAM.puml](C2_Multitenant_IAM.puml) (желтые связи O1-O10) и [Onboarding_Sequence.puml](Onboarding_Sequence.puml). Оркестратор: **Temporal** (долгие процессы с ожиданием людей и внешних систем, ретраи, таймеры, компенсации, видимость состояния).

| Шаг | Что происходит | Исполнитель | Целевое время | Откат |
|:-:|:--|:--|:-:|:--|
| O1 | Партнёр подаёт заявку в Partner Portal: компания, страна, тариф изоляции, функции, данные IdP | Партнёр | Минуты | Отмена заявки |
| O2 | Orchestrator запускает workflow, Tenant Service создаёт тенанта в статусе PENDING | Автоматически | Секунды | Удаление записи |
| O3 | KYB-проверка (асинхронно, вебхук). При высоком риске ручная задача для Compliance officer | Автоматически и человек | От минут до 2 рабочих дней | Статус REJECTED, ресурсы ещё не созданы |
| O4 | Политика страны из Control Plane: регион, схема DR, допустимые PSP и карты, класс изоляции (по [Task3](../Task3/ADR.md#adr-36-стратегия-соответствия-локальным-регуляторным-требованиям)) | Автоматически | Секунды | Нет (чтение) |
| O5 | IAM: Organization, роли и группы, SSO-брокер (метаданные IdP), SCIM-токен, OAuth-клиенты | Автоматически | Минуты | Удаление Organization |
| O6 | Провижининг изоляции: pool (RLS-политики, квоты Kafka, row policy ClickHouse, префикс S3, ключ данных) или silo (кластер БД, топики, KMS, namespace) | Provisioning Controller (GitOps) | Pool 5-15 мин, Silo 1-4 часа | Deprovision в обратном порядке |
| O7 | Конфигурация: шаблоны тарифов, провайдеры платежей и карт, шаблоны уведомлений, флаги, брендинг | Автоматически | Минуты | Откат версии конфигурации |
| O8 | Мониторинг: дашборды SLA, алерты и SLO, синтетические пробы, метки `tenant_id`, учёт использования | Автоматически | Минуты | Удаление дашбордов и правил |
| O9 | Smoke-тест в песочнице (синтетический заказ) и тест изоляции (cross-tenant) | Автоматически | 5-10 мин | При провале: компенсация и алерт SRE |
| O10 | Активация (ACTIVE), событие `TenantOnboarded`, уведомление партнёру с доступами | Автоматически | Секунды | Деактивация |

**Итоговые целевые сроки.** Техническая часть для pool-тенанта до 1 рабочего часа (без ожидания KYB), для silo до 1 рабочего дня. Вся процедура включая KYB, договор и интеграцию партнёра укладывается в 2-4 недели из бизнес-цели, при этом платформа не должна быть узким местом.

**Принципы:**

- Каждый шаг идемпотентен, повторяется с экспоненциальной паузой. Состояние в Temporal переживает рестарты.
- Провижининг как код (Crossplane и Terraform через Argo CD): повторяемость, контроль дрейфа.
- Любая ошибка после O5 запускает компенсацию (Deprovision) и уведомление.
- Все шаги пишут события в аудит и в метрики воронки онбординга.
- Тестовый тенант (песочница) создаётся тем же процессом, ошибки онбординга обнаруживаются регулярным прогоном синтетического партнёра.

### Альтернативы

| Вариант | Почему не выбран |
|:--|:--|
| Сага на Kafka (оркестрация в Booking-подобном стиле, [Task2](../Task2/ADR.md#adr-24-сага-бронирования)) | Для коротких критичных транзакций подходит, но онбординг долгий (дни) с человеком в контуре. Temporal даёт таймеры и видимость |
| Camunda / BPMN-движок | Подходит для процессов с людьми, но тяжелее в эксплуатации для команды. Temporal ближе к коду и тестам |
| Ручной онбординг через тикеты в платформенную команду | Не масштабируется, срок недели, ошибки конфигурации |
| Скрипты Terraform без оркестратора | Нет ретраев, ожиданий, ручных задач и компенсаций |

### Компромиссы и риски

| Риск | Эффект | Смягчение |
|:--|:--|:--|
| Temporal становится новым критичным компонентом | Остановка онбординга при отказе | Не Tier-0 (онбординг не в пути заказа), HA-кластер, процесс возобновляется после восстановления |
| Частично созданные ресурсы после сбоя | Утечки ресурсов и стоимость | Компенсации, периодический сборщик «осиротевших» ресурсов (reconciler) |
| Мошеннический партнёр проходит KYB | Репутационные и финансовые потери | Ручная проверка по риск-скору, ограниченные лимиты и квоты на первые 30 дней, мониторинг аномалий |
| Ошибка в политике страны даёт неверный регион или DR | Нарушение резидентности | Политики в Git с ревью compliance, автотесты политик |
| Рост числа тенантов нагружает Control Plane | Задержка конфигурации | Кэш конфигурации в шлюзе и сервисах, реплики Control Plane в регионах |

## ADR 5.4. Мониторинг мультитенантного окружения

### Контекст

Платформа видна тенанту через SLA, а не через внутренние метрики. Партнёры требуют прозрачности (свои показатели качества) и гарантий, что не видят чужие. Нужно отследить «шумных соседей», учёт использования для биллинга и аномалии безопасности. Общая основа мониторинга описана в [Task2 (ADR 2.6)](../Task2/ADR.md#adr-26-подход-к-мониторингу-и-метрики).

### Требования

- SLI и SLO по каждому тенанту, доступные ему самому.
- Тенант видит только свои данные телеметрии.
- Раннее обнаружение шумных соседей и превышения квот.
- Учёт использования по тенанту.
- Аудит доступа и обнаружение попыток доступа к чужим данным.

### Решение

Компоненты (зелёный цвет) на [C2_Multitenant_IAM.puml](C2_Multitenant_IAM.puml).

| Аспект | Решение |
|:--|:--|
| Метки | `tenant_id` в логах и трейсах всегда. В метриках только в агрегированных рядах (recording rules) по ключевым SLI, чтобы не раздувать кардинальность (допустимо при сотнях тенантов, на тысячах лимит). Метрики по `booking_id` и `driver_id` не создаются |
| Изоляция доступа к телеметрии | Prometheus и Thanos доступны тенанту только через **prom-label-proxy**, принудительно добавляющий фильтр `tenant_id` к запросу. Логи Loki в мультитенантном режиме (X-Scope-OrgID для silo, фильтр по метке для pool). Grafana: папка и права по тенанту (организация для silo). Дашборды встраиваются в Partner Portal |
| SLI/SLO тенанта | Доступность API (доля успешных запросов), p95 латентности, доля успешных заказов, время до назначения водителя, успешность авторизации платежей, доставка вебхуков. Оценка по burn rate |
| Алерты | Платформенные идут SRE. По тенанту (SLO, превышение квоты, ошибки вебхуков) уходят контактам партнёра через Alertmanager и Notification |
| Шумные соседи | Потребление на тенанта: RPS, время БД, байты Kafka, CPU. Сравнение с квотой, алерт при 80%, ограничение при 100%. Дашборд «топ тенантов по ресурсам» |
| Метрики использования (Usage Metering) | Поток событий использования (поездки, API-вызовы, объём событий, хранение) агрегируется Flink и записывается в ClickHouse, источник для биллинга и FinOps (стоимость на тенанта) |
| Безопасность | События в SIEM: входы и отказы, смена ролей, JIT-доступ, раскрытие PII, **попытки cross-tenant доступа (отказы OPA и RLS)**. Любая попытка доступа к чужому тенанту создаёт алерт безопасности |
| Синтетика | Пробы на тестовых тенантах и для enterprise-тенантов на их конфигурации, постоянная проверка изоляции |
| Мониторинг онбординга | Воронка по шагам O1-O10, время шагов, доля неуспешных, зависшие workflow |

**Ключевые метрики мультитенантности:**

| Метрика | Порог: заявка | Порог: вызов |
|:--|:--|:--|
| Cross-tenant попытки (отказы OPA или RLS с признаками подбора) | Любая (аудит) | Более 5 за 5 мин с одного субъекта |
| Любой фактический cross-tenant доступ (нарушение изоляции) | нет | Любой, инцидент безопасности |
| Квота тенанта (API, Kafka, БД) | более 80% | более 100% (ограничение) |
| Доля тенантов с нарушением SLO за 30 дней | более 5% | более 15% |
| Время активации pool-тенанта (O2-O10) p95 | более 30 мин | более 2 ч |
| Зависшие workflow онбординга | более 0 более часа | более 0 более суток |
| Кардинальность метрик с `tenant_id` | более 70% лимита | более 90% лимита |
| Лаг Usage Metering | более 15 мин | более 1 ч (риск неверного биллинга) |

### Альтернативы

| Вариант | Почему не выбран |
|:--|:--|
| Отдельный стек мониторинга на тенанта | Дорого. Оставлен для silo там, где требует договор |
| Доступ тенантов к общему Grafana без фильтра | Риск утечки. Выбран принудительный фильтр на уровне прокси |
| Метка `tenant_id` на всех метриках | Взрыв кардинальности. Только в агрегатах |
| Учёт использования по логам | Неточно и дорого. Выбран поток событий использования |

### Компромиссы и риски

- Принудительный фильтр на прокси единый и критичный: ошибка в нём раскрывает метрики. Он покрывается cross-tenant тестами (запрос тенанта A метрик тенанта B).
- Усечение кардинальности скрывает редкие проблемы у отдельных тенантов: для таких случаев логи и трейсы.
- Метрики использования влияют на биллинг, поэтому нужны сверка и защита от потери событий (outbox и идемпотентность из Task2).
- Раскрытие партнёру внутренних метрик платформы может раскрыть чувствительные данные: публикуются только заранее подготовленные SLI-дашборды.

## ADR 5.5. Потоки данных

### Контекст

Нужно показать, как контекст тенанта проходит через платформу и где его защищают, на диаграмме [C2_Multitenant_IAM.puml](C2_Multitenant_IAM.puml).

### Решение

| Поток | Путь | Контекст тенанта и защита |
|:--|:--|:--|
| Вход и SSO | Пользователь партнёра, Keycloak, IdP партнёра, JWT | `tenant_id` и роли в токене, MFA по политике, короткий срок жизни |
| Запрос API | Клиент, API Gateway, OPA, сервис | Тенант из токена (клиентский игнорируется), квоты, решение политики, mTLS и подписанный `x-tenant-id` |
| Доступ к данным | Сервис, PostgreSQL pool или silo | `SET LOCAL app.tenant_id`, RLS. Для silo маршрут к выделенному кластеру по реестру |
| События | Сервис, Kafka | `tenant_id` в конверте, общие топики для pool, `t.<tenant>.*` для silo, квоты и ACL |
| Аналитика | Kafka, ClickHouse, BI | Row policy по `tenant_id`, маскирование PII на витринах (Task4) |
| Телеметрия | Сервисы, Prometheus, Loki, Grafana | Метки `tenant_id`, доступ через принудительный фильтр |
| Использование и биллинг | Gateway и Kafka, Usage Metering, ClickHouse | Агрегация по тенанту и интервалу |
| Аудит | Keycloak, Gateway, OPA, SIEM | Неизменяемый журнал, видимость владельцу тенанта |
| Онбординг | Partner Portal, Orchestrator, Tenant Service, IAM, Provisioning, Control Plane, Мониторинг | Шаги O1-O10, откат при ошибке |
| Вебхуки | Сервис, система партнёра | Подпись HMAC, повторы с backoff, журнал доставки в Developer Portal |

## ADR 5.6. Роли и уровни доступа к данным

### Контекст

Нужно зафиксировать, кто и к каким данным имеет доступ, чтобы настроить RBAC и ABAC в IAM и OPA и подтвердить принцип наименьших привилегий. Классы данных (P0-P3) определены в [Task3](../Task3/ADR.md#adr-36-стратегия-соответствия-локальным-регуляторным-требованиям).

### Требования

- Наименьшие привилегии и разделение обязанностей.
- Доступ тенанта только к своим данным, сотрудников GoFuture только по необходимости.
- Чувствительные данные (PII, финансы) маскируются по умолчанию.
- Таблица исполнима: каждая ячейка превращается в правило политики.

**Машинные идентичности:**

| Идентичность | Права | Ограничения |
|:--|:--|:--|
| Сервис платформы (SPIFFE) | Чтение и запись только в собственные схемы БД и топики (по ACL сервиса). В контексте тенанта из запроса | mTLS, короткие креды БД из Vault, нет BYPASSRLS |
| Партнёрский API-клиент (OAuth2 client credentials) | Только scope, выданные тенантом (например, `bookings:read`, `bookings:write`) | Квоты, rate limit, ротация ключей, IP allowlist по желанию |
| CI/CD | Деплой в свои namespace, чтение артефактов | Нет доступа к данным тенантов |
| Failover Controller | Управление DNS, лидерами БД и включением ячеек | Действует по кворуму арбитра, все действия аудируются |

**Правила, обеспечивающие матрицу:**

1. **Тенант-скоупинг на трёх уровнях:** gateway (источник тенанта), OPA (совпадение tenant и региона), RLS (последний рубеж).
2. **Маскирование `R*`** выполняется в слое данных или представлениях (телефон `+62 8** *** 1234`, имя до инициалов, карта только токен с последними 4 цифрами). Раскрытие значения требует причины, фиксируется в аудите.
3. **Доступ сотрудников GoFuture к бизнес-данным только JIT.** Без тикета доступа нет, срок до 4 часов, владелец тенанта получает уведомление.
4. **Финансовые операции требуют двух людей** (4-eyes) и step-up MFA. Поддержка не может менять реквизиты.
5. **PA не видит бизнес-данные** (данные тенантов): управляет инфраструктурой. Логи для PA очищены от PII.
6. **Периодическая ресертификация:** раз в квартал владелец тенанта подтверждает список ролей и пользователей, раз в квартал проводится пересмотр доступа сотрудников GoFuture. Неиспользуемые права автоматически отзываются.
7. **Тесты политик:** таблица превращается в тесты OPA (положительные и отрицательные случаи), запрещающие регрессию.

### Альтернативы

| Вариант | Почему не выбран |
|:--|:--|
| Широкие роли («админ», «пользователь») | Нарушают наименьшие привилегии, нельзя разделить финансы и поддержку |
| Постоянный доступ поддержки к данным | Риск злоупотребления и утечки, не проходит аудит |
| Динамическая генерация ролей на тенанта | Взрыв числа ролей. Фиксированный набор ролей плюс атрибуты (ABAC) |
| Доступ платформенных администраторов к данным для отладки | Заменён обезличенной телеметрией и JIT на конкретные инциденты |

### Компромиссы и риски

| Риск | Эффект | Смягчение |
|:--|:--|:--|
| Слишком строгий JIT замедляет поддержку | Рост времени решения обращений | SLA на одобрение (например, 15 минут), предодобренные сценарии для типовых обращений |
| Дрейф политик и ролей | Лишние привилегии | Политики как код, ежеквартальная ресертификация, автоматический отзыв неиспользуемого |
| Ошибки в маскировании | Раскрытие PII | Централизованная библиотека маскирования, тесты, выборочные проверки |
| Таблица не охватывает все новые сущности | Пробелы доступа | Новый тип данных не публикуется без записи в матрице и классификации (условие готовности к проду) |
| Роли партнёров отличаются от шаблона | Запросы на кастомные роли | Тенант может создавать составные роли из набора разрешений, но не выше своего тенанта (ограничение шаблона) |
