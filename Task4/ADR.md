## ADR 4.1. Архитектура пайплайна данных

### Контекст

Компании нужна единая платформа для трёх классов ML-задач: динамическое ценообразование и прогноз спроса, прогноз нагрузки на водителей (антигорячие зоны), обнаружение мошенничества. Сейчас данные лежат в одной БД монолита и в ClickHouse, обработка идёт ETL-процессами (Spark/Flink без единой схемы контрактов). После декомпозиции данные расходятся по десяткам сервисов и четырём регионам, и без общей платформы появятся разные версии одной метрики и неподконтрольный вывоз персональных данных.

Оценка объёма (допущение, A2 из [Task1](../Task1/ADR.md#допущения)): около 160 тыс. событий геопозиции/с по всем регионам, то есть около 14 млрд событий и около 2 ТБ сырых данных в сутки. В Parquet со сжатием около 0,4-0,5 ТБ в сутки. Остальные потоки (заказы, платежи, телеметрия приложений) в десятки раз меньше.

### Требования

| ID | Требование |
|:-:|:--|
| D1 | Единый путь данных из всех микросервисов с единой схемой событий и контрактов |
| D2 | Три скорости: горячий (секунды) для surge и fraud, тёплый (минуты) для оперативных отчётов, холодный (часы) для обучения и сверок |
| D3 | Персональные данные не покидают регион. В глобальный контур идут только псевдонимизированные и агрегированные данные |
| D4 | Признаки для моделей считаются один раз и одинаково для обучения и онлайн-скоринга (без training-serving skew) |
| D5 | Выкладка моделей с канареечным запуском и откатом, без изменения кода сервисов |
| D6 | BI из единой семантики, доступ по ролям и тенантам |
| D7 | Проверка качества данных на каждом слое и измеримые SLA наборов данных |
| D8 | Не нагружать OLTP: источники только через события и CDC с реплик |

### Решение

Диаграмма: [C4_DataPipeline.puml](C4_DataPipeline.puml). Архитектура lakehouse с общим потоком Kafka (Kappa-подход для потоков и пакетные пересчёты поверх lake).

**Слои:**

| Слой | Компоненты | Назначение |
|:--|:--|:--|
| Источники | Доменные события (outbox), CDC (Debezium) по OLTP и legacy-монолиту, клиентская телеметрия, внешние данные (трафик, погода, события города) | Все данные поступают из микросервисов событиями. CDC только для справочников и таблиц без событий. Прямые запросы к OLTP запрещены |
| Приём и контракты | Kafka региона, Schema Registry, Data Contracts (Protobuf плюс правила protovalidate), Stream Validator (Flink) | Проверка контракта на входе. Невалидные события уходят в карантин (DLQ) с причиной, остальные в `clean.*` |
| Потоковая обработка | Flink | Агрегаты по H3-ячейкам и признаки для ML в скользящих окнах (1 минута, 1 час, 24 часа), обогащение справочниками |
| Хранение | Data Lake (S3 и Apache Iceberg: bronze, silver, gold), ClickHouse (оперативные витрины), Redis (online Feature Store) | Iceberg даёт версии, откат и эволюцию схем. ClickHouse отвечает на запросы за секунды. Redis отдаёт признаки менее чем за 5 мс |
| Пакетная обработка | Spark и dbt под управлением Airflow | Пересчёт витрин, обучающие выборки, бэкфилл, сверка |
| Граница региона | Pseudonymization Gate (Flink и KMS) | Удаляет PII, хэширует идентификаторы региональной солью, пропускает только P2 и P3 (классы данных см. Task3) |
| Глобальный контур | Global Kafka, Global Lakehouse, Global ClickHouse, Offline Feature Store | Обучение моделей и кросс-региональные отчёты на псевдонимизированных данных |
| ML и BI | См. ADR 4.2 и 4.3 | |
| Управление данными | Каталог и lineage (DataHub и OpenLineage), Data Quality, Data Observability | Владельцы, классификация PII, происхождение данных, SLA |

**Три скорости данных:**

| Путь | Маршрут | Задержка | Примеры |
|:--|:--|:-:|:--|
| Горячий | Сервис, Kafka (raw), Validator, `clean`, Flink, Online Feature Store, Model Serving, сервис | Секунды | Surge (обновление каждые 10 с), скоринг Fraud (бюджет 150 мс на вызов), подбор водителя |
| Тёплый | `clean`, Kafka Connect, ClickHouse | Десятки секунд | Оперативные дашборды (заказы по минутам, отмены, ETA) |
| Холодный | `clean`, S3 Sink, Iceberg (bronze, затем silver и gold), Spark и dbt, Offline Feature Store | Часы | Обучение моделей, финансовая сверка, бэкфилл |

**Хранение сырой геопозиции.** Сырые точки (около 0,4-0,5 ТБ/сутки) хранятся в bronze 7 суток для переобучения и разбора инцидентов, затем остаются только агрегаты по ячейкам и сжатые треки завершённых поездок (по требованиям хранения Task3: точные геотреки 90 дней).

**Классы данных в потоке.** Валидатор расставляет PII-теги по схеме (`(pii)=true` в Protobuf) и маскирует поля, которые нельзя класть в общий lake (например, номер телефона заменяется на идентификатор пользователя).

### Альтернативы

| Решение | Выбрано | Рассмотрено и отвергнуто | Причина |
|:--|:--|:--|:--|
| Формат таблиц | Apache Iceberg | Delta Lake, Hudi | Нейтральность к движкам (Spark, Flink, ClickHouse читают Iceberg), откат и эволюция схем. Delta привязывает к экосистеме Databricks |
| Аналитическое хранилище | ClickHouse (уже в стеке) | Apache Druid, Pinot, Snowflake | Нет смысла менять: быстро на агрегатах, дёшево, уже эксплуатируется. SaaS-DWH нарушает требования резидентности |
| Архитектура | Kappa плюс пакетный пересчёт по lake | Классическая Lambda (два кода: потоковый и пакетный) | Меньше дублирования логики. Единые определения признаков через Feature Store |
| Приём в lake | Kafka Connect sinks | Flink для всей записи | Коннекторы проще и надёжнее, Flink остаётся для логики |
| Оркестрация | Airflow | Dagster, Argo Workflows | Уже в экосистеме data-инженеров |
| Единая глобальная платформа с PII | Нет | Один глобальный lake | Нарушает резидентность и требования ADR 3.6 из Task3 |

### Компромиссы и риски

| Риск | Эффект | Смягчение |
|:--|:--|:--|
| Рост объёма сырой геопозиции | Стоимость хранения и скорость запросов | Срок bronze 7 суток, партиционирование по часу и ячейке, агрегирование, сжатие zstd, мониторинг стоимости на домен |
| Дублирование платформы в каждом регионе | Стоимость и эксплуатация четырёх копий | Единый шаблон (Helm и Terraform), региональный контур минимальный: Kafka, Flink, lake, ClickHouse. Тяжёлое обучение только в глобальном контуре |
| Задержка псевдонимизации в Gate | Свежесть глобальных данных | Глобальные потребители допускают задержку минуты, горячий путь не идёт через Gate |
| Обратимость псевдонимизации внутри региона | Риск деанонимизации | Региональная соль в KMS, запрет объединения глобальных наборов с региональными ключами, аудит доступа |
| Контракты замедляют команды | Тормоз скорости выхода фич | Автоматическая проверка в CI и шаблон схемы, правила только на критичные поля |
| ClickHouse не рассчитан на частые обновления | Устаревание справочников | Справочники подтягиваются словарями (dictionaries) и пересобираются из lake |

## ADR 4.2. ML-платформа

### Контекст

Три класса моделей должны развиваться независимо от релизов сервисов и без утечки персональных данных. Сейчас ML-пайплайны ведут data-инженеры в Spark без единого реестра моделей и мониторинга дрейфа.

### Требования

- Одни и те же определения признаков для обучения и онлайн-скоринга.
- Воспроизводимость обучения (данные, код, параметры).
- Безопасная выкладка: shadow, канарейка, откат.
- Мониторинг качества и дрейфа в продуктиве.

### Решение

| Модель | Назначение | Признаки (примеры) | Обслуживание | Задержка | Переобучение | Метрики качества |
|:--|:--|:--|:--|:--|:--|:--|
| Прогноз спроса и surge | Динамическое ценообразование, загрузка водителей | Спрос и предложение по ячейке за окна, день недели, погода, события города, трафик | Онлайн (Pricing) и пакетный прогноз по ячейкам каждые 5-15 мин (Dispatch) | p99 менее 50 мс | Ежедневно | WAPE и MAPE по ячейкам, стабильность цены (разброс коэффициента) |
| Fraud-скоринг | Заказы и платежи | Скорость заказов, устройства, смена карт, география, история отмен | Онлайн (Fraud) | p99 менее 100 мс (бюджет 150 мс на вызов в саге) | Еженедельно и по дрейфу | Precision и recall на разметке, доля ложных блокировок, потери от chargeback |
| Прогноз спроса для упреждающего распределения | Перераспределение водителей, ожидание подходящего водителя | Агрегаты по ячейкам, история подач, ETA | Пакетно, результат в `geo.zone-stats` и в Dispatch | Минуты | Ежедневно | Снижение доли заказов в «горячих зонах», время подачи |

**Жизненный цикл:**

1. **Эксперименты:** JupyterHub, выборки из Offline Feature Store (point-in-time join, без утечки будущего).
2. **Обучение:** пайплайны Spark и Python на Kubernetes по расписанию и по сигналу дрейфа. Все запуски пишутся в MLflow (код, версия данных Iceberg-снимка, параметры, метрики).
3. **Реестр моделей (MLflow):** версия, метрики, подпись схемы признаков. Выкладка в продуктив только после одобрения (approval gate): метрики лучше текущей модели и проверка смещения по регионам.
4. **Выкладка:** KServe в каждом регионе. Артефакт модели не содержит данных пользователей, поэтому его можно распространять между регионами. Порядок: shadow (предсказания пишутся, но не используются), канарейка 5-10% трафика, затем 100%, откат одной командой.
5. **Онлайн-признаки:** Flink и материализация из Offline Feature Store в Redis. Одно определение признака (Feast) используется в обучении и в онлайне.
6. **Мониторинг:** Evidently и Prometheus: дрейф признаков (PSI), дрейф предсказаний, качество на отложенной разметке. Просадка запускает переобучение или откат на прошлую версию.
7. **Отказоустойчивость:** при недоступности serving Pricing использует правило (последний известный surge по ячейке из `pricing.surge.v1`), Fraud работает в режиме fail-open с лимитом суммы (см. Task2).

### Альтернативы

| Вариант | Почему не выбран |
|:--|:--|
| Облачная ML-платформа провайдера (SageMaker, Vertex AI) | Привязка к вендору и вопрос данных в регионе. Открытый стек (MLflow, Feast, KServe) работает в любом облаке |
| Feature Store как SaaS (Tecton) | Дорого и данные вне контура. Выбран Feast |
| Обучение отдельно в каждом регионе | Не хватает данных для редких рынков и дороже. Выбрано глобальное обучение на псевдонимизированных данных |
| Федеративное обучение | Сложно эксплуатировать. Останется вариантом для стран со строгой локализацией, если регулятор запретит выгрузку псевдонимизированных данных |

### Компромиссы и риски

- Модель, обученная глобально, может хуже работать на новом рынке (холодный старт). Смягчение: признаки с региональными эффектами и дообучение по региону после накопления данных.
- Риск смещения: модель Fraud может завышать ложные блокировки для отдельных стран. Метрики разбиваются по регионам и сегментам, это условие одобрения модели.
- Динамическое ценообразование это и регуляторный риск (ограничения на рост цены в некоторых странах и в чрезвычайных ситуациях). Ограничения surge задаются правилами в Pricing (потолок множителя по рынку), а не только моделью.
- Сложность стека (Feast, KServe, MLflow, Kubeflow) требует отдельной команды ML-платформы или выделенных инженеров.

## ADR 4.3. BI и доступ к данным

### Контекст

В стеке есть DataLens. Управляемый сервис в Yandex Cloud недоступен в целевых регионах, но есть open-source версия DataLens, которую можно развернуть самостоятельно.

### Требования

Единые метрики (одно определение «поездки», «выручки»), доступ по ролям и тенантам, региональные отчёты не выносят данные из региона.

### Решение

- **DataLens (self-hosted)** на двух уровнях: региональный подключается к региональному ClickHouse (данные остаются в регионе), глобальный к Global ClickHouse (только P2 и P3).
- **Семантический слой** в dbt (метрики и измерения как код), один источник определений. DataLens использует только gold-витрины.
- **Доступ:** SSO через IAM, row-level security по `tenant_id` и `region` (подробно Task5). Данные с PII в BI не попадают, поля маскируются на уровне витрины.
- **Каталог:** DataHub показывает владельца набора, классификацию, свежесть и дашборды, которые на него опираются.

### Альтернативы

Superset, Metabase и Looker рассматривались: Looker это SaaS, а Superset и Metabase равноценны DataLens, но не дают выигрыша для команды, уже работающей с DataLens. Отвергнуто.

### Компромиссы и риски

Self-hosted DataLens требует эксплуатации и обновлений безопасности. Если нагрузка на ClickHouse от BI вырастет, нужна отдельная реплика для запросов BI и лимиты на запросы (квоты).

## ADR 4.4. Механизмы обеспечения качества данных

### Контекст

Дополнительное задание. Ошибка в данных напрямую превращается в бизнес-потери: неверный surge повышает цены, пропущенное событие Fraud пропускает мошенника, ошибка в агрегате выплат водителям это финансовая претензия. Качество нужно контролировать автоматически и на каждом слое, а не в отчёте после инцидента.

### Требования

Измеримые правила по измерениям качества, автоматическая блокировка плохих данных, видимость владельца и SLA, ясный процесс при инциденте.

### Решение

Контроль построен по слоям пайплайна:

| Слой | Измерение качества | Механизм | Инструмент | Порог и действие |
|:--|:--|:--|:--|:--|
| Источник | Валидность, согласованность | **Data Contracts**: Protobuf-схема, правила protovalidate (диапазоны, обязательные поля, enum), проверка совместимости в CI продюсера. Контрактные тесты | Schema Registry, protovalidate, CI | Ломающее изменение не проходит CI |
| Приём | Валидность, уникальность, своевременность | Stream Validator: проверка контракта, дедупликация по `event_id`, обработка поздних событий (допуск по event time), нормализация времени и единиц измерения | Flink | Невалидное в карантин (DLQ) с причиной. Алерт владельцу, если более 0,1% потока за 5 мин |
| Приём | Приватность | Теги PII по схеме, маскирование, проверка запрета экспорта | Flink, каталог | Событие с неразмеченным PII-полем не пропускается в общий lake |
| Хранилище (bronze, silver, gold) | Полнота, уникальность, валидность, ссылочная целостность | Проверки по правилам: not null, уникальность ключей, диапазоны (например, цена больше 0 и меньше порога рынка), справочники, распределение значений | Great Expectations / Soda, dbt tests | Провал критичной проверки блокирует публикацию слоя (gate в Airflow), некритичной создаёт заявку |
| Пайплайн | Своевременность | Мониторинг свежести и объёма набора данных, SLA на набор | Data Observability, Airflow SLA, Prometheus | Сравнение с профилем: объём ниже 70% от нормы за час, свежесть выше SLA, алерт |
| Сквозной | Точность, согласованность | **Сверки (reconciliation):** количество и суммы между OLTP (через CDC), lake и ClickHouse почасово. Финансовая сверка выплат и списаний с данными PSP ежедневно | Spark, dbt | Расхождение выше 0,01% по заказам, любое по деньгам: инцидент |
| Схема | Совместимость | Мониторинг дрейфа схем и неожиданных значений | Data Observability | Новая колонка или тип события создают заявку, а не ломают пайплайн |
| Происхождение | Прослеживаемость | Lineage от источника до дашборда и модели | OpenLineage, DataHub | Оценка воздействия: при падении набора видно, какие дашборды и модели затронуты |
| Владение | Ответственность | Каждый набор данных это продукт с владельцем, описанием, SLA и оценкой качества (DQ score) | DataHub | Набор без владельца не допускается в gold |
| ML | Качество признаков и моделей | Единые определения признаков (Feast), валидация признаков перед обучением, проверка утечки будущего (point-in-time join), PSI для дрейфа, shadow и канарейка | Feast, Evidently, MLflow | PSI выше 0,2 по важному признаку: алерт и переобучение, просадка качества: откат модели |

**Процесс при нарушении качества.**

1. Автоматический алерт владельцу набора с ссылкой на проверку и lineage.
2. Карантин: плохие события остаются в DLQ, публикация слоя блокируется, потребители продолжают работать с последней хорошей версией (Iceberg snapshot).
3. Исправление источника или правила, повторная обработка DLQ (replay) или бэкфилл.
4. Постмортем для инцидентов уровня «деньги или цены», обновление правила или контракта.

**Показатели качества данных (SLO набора):** свежесть (например, gold-витрина заказов не позже 15 минут), полнота (не менее 99,9% ожидаемых записей), доля карантина (менее 0,1%), доля пройденных проверок (не менее 99%).

### Альтернативы

| Вариант | Почему не выбран |
|:--|:--|
| Проверки только на дашбордах и по жалобам | Реактивно, дорого по последствиям |
| Единая «большая» проверка в конце пайплайна | Поздно и без локализации причины. Выбран контроль на каждом слое |
| Жёсткая блокировка любого нарушения | Остановит пайплайн из-за мелочей. Разделены критичные (блокируют) и некритичные (заявки) проверки |
| Полная «ручная» сверка | Не масштабируется, не работает на 160 тыс. событий/с |

### Компромиссы и риски

| Риск | Эффект | Смягчение |
|:--|:--|:--|
| Слишком много правил, много ложных алертов | Дежурные перестают реагировать | Приоритеты правил, бюджет алертов, регулярный пересмотр |
| Проверки замедляют пайплайн | Рост задержки gold | Проверки на горячем пути только лёгкие (контракт, дедуп), тяжёлые на пакетном слое |
| Валидатор в потоке становится узким местом | Задержка всех потоков | Масштабирование по партициям, проверка нагрузки (160 тыс. событий/с), отдельный job на тип потока |
| Неверные пороги сверки | Пропуск или ложные срабатывания | Калибровка на исторических данных, пороги по домену |
| Скрытая зависимость потребителей от плохих данных | Поломка при исправлении | Lineage и уведомление потребителей, версионирование наборов |
