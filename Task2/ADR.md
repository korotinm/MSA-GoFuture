## ADR 2.1. Модель доменных событий

### Контекст

Сервисы должны общаться событиями, чтобы выдержать пик и не падать каскадом. Для этого нужен единый формат событий и каталог, иначе каждая команда придумает свой, и подключить потребителя без согласования будет нельзя.

### Требования

- Единый конверт (envelope) для всех событий.
- Каталог событий с владельцем и потребителями.
- Эволюция схем без поломки потребителей.

### Решение

**Конверт события** (Protobuf, схема в Schema Registry, режим совместимости BACKWARD):

```protobuf
message EventEnvelope {
  string event_id       = 1;   // UUIDv7, ключ идемпотентности у потребителя
  string event_type     = 2;   // "BookingCreated"
  uint32 event_version  = 3;   // версия схемы payload
  string aggregate_type = 4;   // "Booking"
  string aggregate_id   = 5;   // booking_id, он же ключ партиции
  uint64 aggregate_seq  = 6;   // монотонный номер версии агрегата (защита от перестановки)
  string region         = 7;   // "sgp" | "jkt" | "gru" | "qro"
  string tenant_id      = 8;   // партнёр (Task5)
  google.protobuf.Timestamp occurred_at = 9;   // время события (event time)
  string correlation_id = 10;  // booking_id для всей цепочки саги
  string causation_id   = 11;  // event_id события-причины
  string trace_id       = 12;  // W3C traceparent, сквозная трассировка
  google.protobuf.Any payload = 13;
}
```

Типовое событие (поле `payload` для `BookingCreated`):

```protobuf
message BookingCreated {
  string booking_id = 1;  string passenger_id = 2;
  GeoPoint pickup = 3;    GeoPoint dropoff = 4;
  string h3_cell = 5;     // H3 res 8 для спроса и surge
  Money  quoted_price = 6; string tariff_id = 7;
  string payment_method_token = 8;   // токен, не данные карты
}
```

**Каталог событий** (владелец публикует, остальные только читают):

| Домен | События | Владелец | Основные потребители |
|:--|:--|:--|:--|
| Booking | `BookingCreated`, `BookingConfirmed`, `BookingCancelled`, `TripStarted`, `TripCompleted` | Booking | Dispatch, Pricing (спрос), Fraud, Payments, Analytics, Notification |
| Driver | `DriverStatusChanged` (online, busy, offline), `DriverRegistered` | Driver | Dispatch, Analytics |
| Geography | `DriverLocationUpdated`, `ZoneDemandChanged` (из Flink) | Geography | Geography (индекс), Flink, Dispatch, Pricing |
| Dispatch | `DriverSearchRequested` (команда), `DriverOfferSent`, `DriverOfferDeclined`, `DriverAssigned`, `DriverNotFound`, `DriverSearchCancelled` (команда) | Dispatch | Booking (оркестратор), Notification |
| Pricing | `PriceQuoted`, `SurgeUpdated` | Pricing | Booking, Analytics |
| Payments | `PaymentAuthorizationRequested` (команда), `PaymentAuthorized`, `PaymentAuthorizationFailed`, `PaymentHoldReleaseRequested` (команда), `PaymentHoldReleased`, `PaymentCaptured`, `RefundIssued`, `PayoutScheduled`, `PayoutCompleted` | Payments | Booking, Fraud, Analytics, Notification |
| Fraud | `FraudCheckPassed`, `FraudCheckRejected`, `FraudSuspected` | Fraud | Booking, Payments, Analytics |
| Notification | `NotificationRequested`, `NotificationSent`, `NotificationFailed` | Notification | Analytics |

**Правила эволюции схем.**

1. Разрешено только добавление необязательных полей. Удаление и смена типа запрещены.
2. Ломающее изменение это новая версия топика (`*.v2`). Старый и новый публикуются параллельно на период миграции потребителей (не менее 3 месяцев).
3. Совместимость проверяется в CI сервиса-продюсера (Schema Registry compatibility check).
4. Команды (`*Requested`, `*Search*`) и события (`*ed`, `*Updated`) различаются в имени и живут в разных топиках: команда адресована одному сервису, событие факт для всех.

### Альтернативы

- **JSON без схемы.** Проще в старте, но поломки потребителей обнаруживаются на проде. Отвергнуто.
- **Avro вместо Protobuf.** Равноценно по совместимости. Protobuf выбран, потому что те же схемы используются в gRPC между сервисами, и код генерируется для Python и Go.
- **События-уведомления без данных (только id).** Снижают размер, но заставляют потребителей ходить в API источника: нагрузка и связность возвращаются. Выбраны события с достаточным состоянием (event-carried state transfer) для критичных потоков.

### Компромиссы и риски

- Протобуфные события с вложенным `Any` усложняют отладку: нужен инструмент просмотра с декодированием (Kafka UI и схема из Registry).
- Дублирование данных (проекции) у потребителей. Риск устаревания закрывается `aggregate_seq` и периодической сверкой.
- Дисциплина версий: без автоматической проверки в CI правила нарушатся быстро.

## ADR 2.2. Схема топиков Kafka и партиционирование по регионам

### Контекст

Регион это единица изоляции: данные граждан остаются в регионе (Task3), отказ региона не должен затрагивать другие, а задержка между регионами 100-300 мс несовместима с обработкой поездок в реальном времени.

### Требования

- События поездки обрабатываются в регионе, где она происходит.
- Порядок событий сохраняется в пределах агрегата (заказ, водитель).
- Критичные топики реплицируются на резерв, обезличенные данные уходят в глобальную аналитику.

### Решение

**Регион = отдельный Kafka-кластер** (3 зоны доступности, RF=3, `min.insync.replicas=2`, rack awareness). Имена топиков в кластерах одинаковые, регион задаётся самим кластером и полем `region` в конверте. Внутри кластера партиционирование идёт по ключу агрегата. Такая схема даёт физическую изоляцию по регионам без зашивания региона в имя топика.

При репликации в другой кластер MirrorMaker 2 добавляет префикс кластера-источника (`sgp.booking.events.v1`), и в глобальном кластере регион становится частью имени топика.

| Топик | Ключ | Партиций | Хранение | Очистка | Продюсер | Консьюмеры | Класс доставки |
|:--|:--|:-:|:-:|:--|:--|:--|:-:|
| `booking.events.v1` | `booking_id` | 48 | 7 дней | delete | Booking (outbox) | Dispatch, Fraud, Pricing, Flink, Payments, Analytics | A |
| `driver.location.v1` | `driver_id` | 64 | 24 ч | delete | Geography | Geography (индекс), Flink | C |
| `driver.events.v1` | `driver_id` | 24 | 7 дней | delete | Driver (outbox) | Dispatch, Analytics | B |
| `geo.zone-stats.v1` | `h3_cell` | 12 | compact + 1 день | compact, delete | Flink | Pricing, Dispatch | B |
| `pricing.surge.v1` | `h3_cell` | 12 | compact + 1 день | compact, delete | Pricing | Pricing (кэш), Booking | B |
| `dispatch.commands.v1` | `booking_id` | 24 | 3 дня | delete | Booking | Dispatch | A |
| `dispatch.events.v1` | `booking_id` | 24 | 7 дней | delete | Dispatch (outbox) | Booking, Notification | A |
| `payments.commands.v1` | `booking_id` | 12 | 7 дней | delete | Booking | Payments | A |
| `payments.events.v1` | `booking_id` | 12 | 30 дней + архив S3 | delete | Payments (outbox) | Booking, Fraud, Notification, Analytics | A |
| `fraud.events.v1` | `subject_id` | 12 | 7 дней | delete | Fraud | Booking, Payments, Analytics | B |
| `notification.requests.v1` | `user_id` | 24 | 3 дня | delete | Booking, Payments, Dispatch | Notification | B |
| `<topic>.retry.1m`, `.retry.10m`, `.dlq` | как у основного | 25-100% от основного | 14 дней (DLQ) | delete | потребитель при ошибке | потребитель, оператор | A |

**Размер партиций.**

- `driver.location.v1`: пик региона около 64 тыс. событий/с, то есть около 1 тыс. событий/с на партицию (64 партиции), поток около 10 МБ/с на регион (событие около 150 Б с накладными). Запас ×4 по пропускной способности и по параллелизму потребителей Flink.
- Остальные топики имеют гораздо меньшую нагрузку (`booking.events` около 1,4 тыс. событий/с на пике региона), но число партиций нельзя уменьшить, а увеличение ломает соответствие «ключ, партиция». Поэтому закладывается запас в 5-10 раз. Стоимость лишней партиции мала: суммарно около 270 партиций основных топиков на регион (при RF=3 менее 1000 реплик на кластер, при пределе порядка 4000 на брокер).
- Хранение `driver.location.v1` 24 часа: около 0,9 ТБ/сутки, с RF=3 около 2,6 ТБ на регион.

**Ключ партиции и порядок.** Ключ равен идентификатору агрегата, поэтому все события одного заказа или водителя попадают в одну партицию и читаются по порядку. Для заказа это даёт упорядоченность `BookingCreated, PaymentAuthorized, DriverAssigned, TripCompleted`. Топики `geo.zone-stats` и `pricing.surge` ключуются по H3-ячейке, а политика `compact` оставляет последнее значение на ячейку: новый потребитель сразу получает актуальное состояние.

**Репликация между кластерами (MirrorMaker 2).**

- На DR-кластер парного региона реплицируются только топики класса A (booking, payments, dispatch), с трансляцией офсетов потребителей.
- В глобальный аналитический кластер идут обезличенные агрегаты и события без персональных данных (подробности в Task3 и Task4).
- `driver.location.v1` между регионами не реплицируется: данные эфемерные, индекс восстанавливается из потока за минуты.

### Альтернативы

- **Один глобальный кластер с партиционированием по региону.** Отвергнуто: задержка записи между континентами, общий отказ всех регионов и нарушение требований хранения данных в регионе.
- **Один топик на регион внутри общего кластера (`sgp.booking.events`).** Отвергнуто по тем же причинам. Остаётся допустимым только внутри глобального аналитического кластера.
- **Партиционирование по H3-ячейке для всех топиков.** Даёт локальность при гео-обработке, но перекос на центральные ячейки (hot partitions) и неупорядоченность событий заказа. Выбрано ключом `h3_cell` только для агрегатов состояния (`zone-stats`, `surge`).

### Компромиссы и риски

- Много кластеров это больше операционной работы и стоимости (4 региона на основном контуре плюс DR и глобальный). Автоматизация через Strimzi/Helm и единые runbook обязательна.
- Горячие партиции: водитель с аномально высокой частотой обновлений перегружает одну партицию. Смягчение: ограничение частоты на стороне Geography (не чаще 1 события в 2 секунды на водителя) и мониторинг skew партиций.
- Размер `driver.location`: рост числа водителей напрямую растит диски. Нужны алерты на заполнение (см. ADR 2.6).

## ADR 2.3. Потоковая обработка: Flink и лёгкие консьюмеры

### Контекст

Динамическое ценообразование и борьба с горячими зонами требуют агрегатов спроса и предложения по ячейкам в окнах по времени события. Fraud требует признаков по истории действий.

### Требования

- Окна по времени события (event time), устойчивые к позднему и неупорядоченному приходу.
- Состояние большого размера, восстановление после сбоя без потерь.
- Обновление surge каждые 10 секунд (NFR-06).

### Решение

**Flink** для сквозной stateful-обработки (в стеке компании Spark/Flink уже есть):

| Job | Вход | Логика | Выход |
|:--|:--|:--|:--|
| `ZoneStats` | `driver.location.v1`, `booking.events.v1` | keyBy(`h3_cell`), tumbling-окно 10 с по event time, watermark с допуском 5 с, allowed lateness 10 с. Считает число свободных водителей и новых заказов, коэффициент давления | `geo.zone-stats.v1` (exactly-once, транзакционный sink) |
| `FraudFeatures` | `booking.events.v1`, `payments.events.v1` | Скользящие окна (1 мин, 1 ч, 24 ч) по пассажиру, водителю, устройству и карте | Онлайн-хранилище признаков (Redis) и ClickHouse |

Состояние в RocksDB, checkpoint каждые 10 с в объектное хранилище, режим EXACTLY_ONCE. Масштабирование по числу партиций `driver.location.v1`.

Бизнес-правила остаются в сервисах: Pricing превращает `ZoneDemandChanged` в коэффициент по тарифным правилам тенанта, Dispatch использует те же статистики для избегания горячих зон. Flink только агрегирует.

**Лёгкие консьюмеры** в сервисах (Python, Go): обновление проекций (Dispatch строит у себя локальное состояние заказов и водителей), саговые обработчики, Notification. Состояние небольшое, окна не нужны, отдельный кластер потоковой обработки не оправдан.

### Альтернативы

| Вариант | Почему не выбран |
|:--|:--|
| Kafka Streams (KStreams) | Только JVM, а сервисы на Python и Go. Для окон и большого состояния подходит, но потребовал бы отдельных JVM-сервисов. Остаётся вариантом, если команда Analytics предпочтёт JVM-приложения |
| Spark Structured Streaming | Микробатчи дают задержку порядка секунд и менее предсказуемы для окон в 10 с. Хорош для пакетной обработки и обучения моделей (Task4) |
| Всё в сервисах | Дублирование состояния и окон в каждом сервисе, сложная проверка корректности |

### Компромиссы и риски

- Flink это отдельная эксплуатационная компетенция (checkpoint, state, backpressure). Нужны runbook и обучение SRE и data-инженеров.
- Поздние события за пределом allowed lateness теряются в агрегате: surge может быть неточным на 1-2 окна при сетевых проблемах. Для ценообразования это допустимо, а точные данные считаются пакетно (Task4).
- Рост состояния при увеличении числа ячеек. Нужны TTL состояния и мониторинг размера.

## ADR 2.4. Сага бронирования

### Контекст

Бронирование затрагивает Booking, Payments, Dispatch (и предусловия Pricing и Fraud). У каждого сервиса своя БД, поэтому глобальной транзакции нет. Нужен механизм, который сохраняет согласованность и гарантированно откатывает уже выполненные шаги.

### Требования

- Не оставлять «зависший» холд денег и «висящие» заказы.
- Прозрачность процесса для эксплуатации (где застрял заказ).
- Таймауты и устойчивость к повторной доставке.

### Решение

**Вид саги: оркестрация** с оркестратором в Booking Service. Диаграмма: [Saga_Booking_Sequence.puml](Saga_Booking_Sequence.puml).

Оркестратор хранит состояние в таблице `saga_instance(booking_id, state, step, deadline_at, attempts, version)` в БД Booking. Команда публикуется через outbox, ответы читаются из топиков `payments.events` и `dispatch.events`. Для каждого шага есть таймаут, а фоновая задача (reaper, каждые 5 с) находит просроченные саги и запускает компенсацию.

**Предусловия без побочных эффектов** (синхронные вызовы, компенсация не нужна):

- Проверка котировки: цена зафиксирована подписанным токеном (TTL 2 минуты), резервирования нет.
- Проверка Fraud (gRPC, таймаут 150 мс): при недоступности fail-open в пределах лимита суммы.

**Шаги с побочными эффектами:**

| № | Шаг | Команда | Успех | Отказ | Компенсация | Таймаут |
|:-:|:--|:--|:--|:--|:--|:-:|
| 1 | Создать заказ PENDING | локальная транзакция | `BookingCreated` | нет | `BookingCancelled` | нет |
| 2 | Холд оплаты | `PaymentAuthorizationRequested` | `PaymentAuthorized` | `PaymentAuthorizationFailed` | Отмена заказа (холда ещё нет) | 30 с |
| 3 | Назначить водителя | `DriverSearchRequested` (TTL 90 с) | `DriverAssigned` | `DriverNotFound` или таймаут | `PaymentHoldReleaseRequested`, затем `PaymentHoldReleased` и `BookingCancelled` | 90 с |
| 4 | Подтвердить заказ | локальная транзакция | `BookingConfirmed` | нет | нет | нет |

Точка невозврата: `DriverAssigned`. Отмена после неё это бизнес-процесс (политика отмены, штраф), а не компенсация саги.

После `TripCompleted` списание (`PaymentCaptured`) и выплата водителю (`PayoutScheduled`, `PayoutCompleted`) идут **хореографией**: результат ни на кого не влияет синхронно, и оркестратор не нужен.

**Гонки.** Если водитель принял заказ, когда сага уже отменила его по таймауту, Booking отвечает на `DriverAssigned` событием `DriverAssignmentRejected`, а Dispatch освобождает водителя. Конечный автомат оркестратора принимает только допустимые переходы, остальные события игнорирует и фиксирует.

### Альтернативы

| Вариант | Плюсы | Почему не выбран |
|:--|:--|:--|
| Хореографическая сага (всё на событиях) | Нет центрального компонента | Логику отката и таймаутов сложно увидеть и отлаживать при 4+ участниках, циклические зависимости. Оставлена для хвоста после поездки |
| 2PC / XA | Привычная модель | Блокировки, не работает с внешним PSP, не масштабируется. Отвергнуто |
| Внешний движок (Temporal, Camunda) | Готовые таймеры, ретраи, UI | Новый критичный компонент и стоимость эксплуатации на пути 500 тыс. поездок. Рассматривается в Task5 для онбординга, где задержки не критичны |

### Компромиссы и риски

- Оркестратор в Booking концентрирует логику. Дисциплина: только координация, бизнес-правила остаются в участниках.
- Постоянная нагрузка на таблицу `saga_instance` (около 170 саг/с на регион в пике). Нужны партиционирование по дате и очистка завершённых записей.
- Зависшая сага при потере дедлайн-обработчика. Мониторинг: счётчик саг с `deadline_at` в прошлом более чем на 60 с (алерт уровня page).
- Fail-open для Fraud: часть мошеннических заказов пройдёт на время сбоя. Смягчение: лимит суммы и постпроверка по `FraudSuspected`.

## ADR 2.5. Надёжная доставка событий

### Контекст

Потеря `PaymentAuthorized` или `DriverAssigned` приводит к потере заказа или денег. При этом для геопозиций стоимость гарантий нецелесообразна: 160 тыс. событий/с, а следующее обновление приходит через 4 секунды.

### Требования

Потеря событий недопустима для заказов и платежей (NFR-11). Для телеметрии допустима потеря малой доли. Дубликаты не должны менять результат.

### Решение

Классы доставки:

| Класс | Топики | Гарантия | Как достигается |
|:-:|:--|:--|:--|
| A (критичный) | booking, payments, dispatch | At-least-once плюс идемпотентность = эффективно ровно один раз | Outbox, `acks=all`, идемпотентный продюсер, ручной commit после обработки, inbox, retry и DLQ |
| B (важный) | driver.events, fraud, notification, zone-stats, surge | At-least-once | `acks=all`, retry, DLQ |
| C (телеметрия) | driver.location | At-most-once допустимо | `acks=1`, батчинг (`linger.ms=20`), сжатие zstd, устаревшие события отбрасываются по `occurred_at` |

**Механизмы.**

1. **Transactional Outbox.** Событие пишется в таблицу `outbox` той же локальной транзакцией, что и изменение данных. Debezium читает WAL и публикует в Kafka (Outbox Event Router). Запись в outbox удаляется в той же транзакции, чтобы таблица не росла (WAL сохраняет вставку). Двойной записи «БД плюс Kafka» нет.
2. **Продюсер.** `enable.idempotence=true`, `acks=all`, `retries` бесконечно с `delivery.timeout.ms=120000`, `max.in.flight.requests.per.connection=5` (порядок сохраняется при идемпотентности). Брокеры: `min.insync.replicas=2`, `unclean.leader.election.enable=false`.
3. **Консьюмер.** `enable.auto.commit=false`, коммит офсета после успешной обработки. **Inbox**: таблица `processed_events(event_id)` в БД потребителя, проверка и бизнес-изменение в одной транзакции. Повторная доставка не меняет результат.
4. **Порядок.** Ключ равен агрегату. Дополнительно проверяется `aggregate_seq`: событие с меньшим номером отбрасывается, с пропуском помещается в retry до прихода предыдущего (до 3 попыток).
5. **Повторы.** Ошибка, которую можно повторить, отправляет сообщение в `*.retry.1m`, затем `*.retry.10m`, затем в `*.dlq`. Ошибки данных (poison pill) идут сразу в DLQ. Для класса A любое сообщение в DLQ это алерт, у каждого DLQ есть инструмент повторной обработки (replay) с сохранением ключа.
6. **Flink.** Checkpoints плюс транзакционный Kafka sink (EXACTLY_ONCE), потребители результата читают с `isolation.level=read_committed`.
7. **Время жизни команд.** У `DriverSearchRequested` и подобных есть TTL: устаревшую команду потребитель отбрасывает.
8. **Межрегиональный отказ.** MirrorMaker 2 с трансляцией офсетов. При переключении возможны повторы за последние секунды, поэтому идемпотентность потребителей обязательна, а не опциональна.
9. **Схемы.** Событие, не прошедшее проверку схемы, не публикуется: ошибка у продюсера, а не у потребителей.

### Альтернативы

- **Транзакции Kafka (`transactional.id`) от сервиса.** Решают запись в Kafka, но не атомарность с БД сервиса. Outbox закрывает именно эту проблему.
- **Двойная запись в БД и Kafka с компенсацией.** Отвергнуто: окно расхождения, нет атомарности.
- **Exactly-once для всех топиков.** Дорого и не нужно для телеметрии.

### Компромиссы и риски

| Риск | Эффект | Смягчение |
|:--|:--|:--|
| Отставание или остановка Debezium | События заказа и платежей не публикуются, саги упираются в таймауты | Алерт на возраст самой старой записи outbox и `MilliSecondsBehindSource`, Connect в distributed-режиме с автоперезапуском |
| Рост WAL из-за зависшего слота репликации | Переполнение диска БД сервиса | Лимит `max_slot_wal_keep_size`, алерт на размер удерживаемого WAL |
| Retry-топики нарушают порядок | Событие обработано не в своём порядке | Проверка `aggregate_seq` |
| Рост DLQ без разбора | Скрытая потеря заказов | Алерт при глубине DLQ больше 0 для класса A, ежедневный разбор |
| Дубликаты после failover региона | Двойное списание | Идемпотентные ключи у PSP по `booking_id`, inbox |
| Потеря геопозиций (класс C) | Неточный индекс на несколько секунд | Следующее обновление заменяет состояние, TTL записи в индексе 15 с |

## ADR 2.6. Подход к мониторингу и метрики

### Контекст

Текущий мониторинг (Prometheus, Grafana, Loki, Alertmanager, экспортеры PostgreSQL и RabbitMQ) работает без сложных настроек и не знает о Kafka, Flink и сагах. При асинхронной архитектуре отказы становятся невидимыми: запрос вернул 202, а заказ завис на шаге 3.

### Требования

- 100% покрытие критических метрик и алертов (цель кейса через 2 месяца).
- Видимость сквозной латентности цепочки событий и состояния саг.
- MTTR не более 15 минут для Tier-0 (NFR-07).
- Дежурный получает только значимые алерты, с инструкцией, что делать.

### Решение

**Принципы.**

1. **От SLO к алертам.** Для Tier-0 определены SLI и SLO. Алерты строятся по скорости сжигания бюджета ошибок (burn rate) на двух окнах: 5 минут и 1 час для немедленного вызова, 30 минут и 6 часов для заявки. Алерты по симптомам (пользователь страдает), а не по причинам (CPU 80%).
2. **Три уровня.** (а) инфраструктура платформы: Kafka, Flink, Connect; (б) поток данных: лаг, задержка событий, DLQ, outbox; (в) бизнес-процесс: саги, подбор водителя, платежи.
3. **Три сигнала.** Метрики, структурированные логи и трейсы связываются через `trace_id`. Trace_id передаётся в заголовках Kafka от шлюза до всех консьюмеров.
4. **Региональность.** Prometheus и Loki работают в каждом регионе (отказ одного региона не слепит остальные), глобальный вид собирается через Thanos.
5. **Каждый алерт имеет runbook, владельца и приоритет.** Алерт без действия удаляется.
6. **Контроль кардинальности.** Метки `tenant_id` и `region` только в агрегированных метриках. Метрики на уровне `driver_id`, `booking_id` не создаются (для них логи и трейсы).

**Метрики и пороги.**

*Kafka (брокеры и топики):*

| Метрика | Порог: заявка | Порог: вызов дежурного |
|:--|:--|:--|
| `OfflinePartitionsCount` | нет | больше 0 |
| `UnderReplicatedPartitions` | больше 0 более 5 мин | больше 0 более 10 мин |
| `ActiveControllerCount` | нет | не равно 1 |
| Сжатие ISR (`IsrShrinksPerSec`) | больше 0 на 10 мин | устойчиво |
| p99 латентности produce | больше 100 мс | больше 500 мс |
| Заполнение диска брокера | больше 75% | больше 85% |
| Skew партиций (разброс размера и трафика) | больше 3× от медианы | нет |

*Продюсеры и outbox:*

| Метрика | Порог: заявка | Порог: вызов |
|:--|:--|:--|
| Возраст самой старой неопубликованной записи outbox | больше 5 с | больше 30 с |
| `MilliSecondsBehindSource` (Debezium) | больше 5 с | больше 30 с |
| WAL, удерживаемый слотом репликации | больше 2 ГБ | больше 5 ГБ |
| Доля ошибок отправки (`record-error-rate`) | больше 0,1% | больше 1% |

*Консьюмеры:*

| Метрика | Порог: заявка | Порог: вызов |
|:--|:--|:--|
| Лаг по времени (возраст самого старого необработанного) для класса A | больше 10 с | больше 30 с |
| Лаг `driver.location` | больше 3 с | больше 5 с (NFR-02) |
| Частота ребалансировок группы | больше 3 за 10 мин | нет |
| Поток в `*.retry.*` | рост в 3 раза к норме | нет |
| Глубина DLQ, класс A | нет | больше 0 |
| Глубина DLQ, класс B | больше 100 | нет |
| Ошибки десериализации и схемы | больше 0 | больше 10 за 5 мин |

*Flink:*

| Метрика | Порог: заявка | Порог: вызов |
|:--|:--|:--|
| Длительность checkpoint p95 | больше 30 с | нет |
| Неудачные checkpoint подряд | нет | 3 и более |
| Backpressure | больше 0,5 в течение 5 мин | больше 0,8 в течение 5 мин |
| Отставание watermark от времени (watermark lag) | больше 15 с | больше 30 с |
| Рестарты job | больше 1 в час | больше 3 в час |
| Размер состояния (рост за сутки) | больше 30% | нет |

*Сквозные метрики и бизнес-SLI:*

| Метрика | Порог | Связь с требованием |
|:--|:--|:--|
| Задержка от `DriverLocationUpdated` до записи в индекс, p99 | больше 2 с (вызов) | NFR-06 (1 с) |
| Свежесть surge: время с последнего `SurgeUpdated` по ячейке | больше 30 с (заявка) | NFR-06 (10 с) |
| Время от `BookingCreated` до первого `DriverOfferSent`, p95 | больше 3 с (вызов) | NFR-05 |
| Успешность создания заказа (SLI, burn rate) | SLO 99,99% | NFR-03 |
| Успешность авторизации платежа | падение ниже 97% (вызов) | Payments |
| Число саг в работе (in-flight) | выход за 2σ от профиля | Capacity |
| Длительность саги до `BookingConfirmed`, p95 | больше 10 с (заявка) | UX |
| Доля компенсированных саг | больше 5% (заявка), больше 15% (вызов) | Качество подбора и платежей |
| Саги с просроченным дедлайном и не завершённые более 60 с | больше 0 (вызов) | Зависшие заказы |
| Доля сработавшего fail-open в Fraud | больше 1% (заявка) | Риск мошенничества |

### Альтернативы

- **SaaS-мониторинг (Datadog, New Relic).** Быстрый старт, но дорого при сотнях тысяч временных рядов, ограничение по хранению данных в регионе и зависимость от вендора. Отвергнуто.
- **Только метрики брокера и лаг.** Не видит зависших саг и деградации бизнес-метрик при «здоровой» инфраструктуре. Недостаточно.
- **ELK вместо Loki.** Богаче для полнотекстового поиска, но дороже в хранении и эксплуатации. Структурированные логи с `trace_id` хорошо работают в Loki, и он уже используется.

### Компромиссы и риски

- Новые компоненты (Tempo, OTel Collector, Thanos) повышают нагрузку на платформенную команду. Нужна поэтапность: сначала метрики и алерты (первые 2 месяца), затем трейсы.
- Слишком много алертов приведёт к «слепоте» дежурного. Бюджет: не более 2 вызовов на дежурство в среднем, остальное в заявки.
- Мониторинг самой платформы мониторинга: Prometheus регионального уровня резервируется (две реплики), для Alertmanager включается кластерный режим и «мёртвая ручка» (watchdog-алерт во внешний контур).
- Рост кардинальности метрик при добавлении тенантов (Task5): учитывается лимит на метки.

## ADR 2.7. Инструменты мониторинга и их отражение на C2

### Решение

| Инструмент | Статус | Роль | На C2 ([C2_EventPlatform.puml](C2_EventPlatform.puml)) |
|:--|:--|:--|:--|
| Prometheus | Существует | Метрики региона, recording rules, SLO-правила. Две реплики на регион | `prom` |
| Thanos (или VictoriaMetrics) | Новый | Долгое хранение и глобальный запрос по регионам | `thanos` |
| Grafana | Существует | Дашборды Kafka, Flink, саг, бизнес-SLI. Provisioning из Git | `grafana` |
| Loki | Существует | Структурированные логи с `trace_id` | `loki` |
| Alertmanager + on-call | Существует, дополняется | Маршрутизация, эскалация, дедупликация, watchdog | `alertmgr` |
| OpenTelemetry Collector | Новый | Единая точка приёма метрик, логов, трейсов от сервисов, пропагация `trace_id` через заголовки Kafka | `otel` |
| Tempo | Новый | Распределённые трейсы в объектном хранилище | `tempo` |
| JMX Exporter, KMinion (лаг групп), Flink Prometheus reporter, Debezium JMX | Новые | Метрики брокеров, групп, джобов, коннекторов | `exporters` |
| Kafka UI (AKHQ) | Новый | Просмотр топиков, групп и DLQ, replay | `akhq` |
| PostgreSQL Exporter | Существует | Метрики БД сервисов и размер WAL слотов | подключается к БД сервисов (не показано) |
| RabbitMQ Exporter | Существует | Только до вывода монолита из эксплуатации | снимается вместе с RabbitMQ |

Мониторинговые контейнеры и связи сбора выделены на диаграмме зелёным цветом.

### Компромиссы и риски

- Версии и совместимость: Thanos и VictoriaMetrics взаимозаменяемы, выбор фиксируется на пилоте в первом регионе (критерий: стоимость хранения 15 месяцев метрик и простота эксплуатации).
- OTel-инструментация требует доработок во всех сервисах: заводится как часть шаблона нового сервиса и как условие готовности к проду (NFR-18).
